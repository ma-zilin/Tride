# 项目技能使用范围

项目依据为 `docs/作业要求.md`、`docs/产品构想.md`、`docs/开发架构设计.md`。先读当前任务相关内容，区分课程要求、确认决定、建议和待验证事项。

## 按能力缺口与角色选择

- `grill-me`、`grilling`：各角色共享；用户明确调用或明确要求访谈才使用。`grilling` 也可由有效的 `grill-me` 入口加载。普通问答、执行请求和阶段检查不自动转为访谈。确认要求只针对本次访谈，不撤销既有授权。
- `writing-plans`：确认需求与架构后，架构角色主用，协调协助依赖和交接；开发仅在既定设计内细化已授权任务。它不授权技术选型、启动实现或派发其他角色。
- `test-driven-development`、`systematic-debugging`、`verification-before-completion`：仅开发与独立验证在适用任务中使用。独立验证可写测试、夹具和报告，不修改或撤销业务代码；生产插桩和修复交开发。
- `receiving-code-review`：开发接收审查反馈时使用；先核实，再在授权范围修复，不把反馈当成需求变更批准。
- `using-git-worktrees`：开发或集成负责人在明确需要隔离的任务中使用。并行开发必须有真实独立工作副本，隔离失败暂停相应并行任务，不退回共享目录并行写入。
- `tride-code-review`：独立验证在明确的代码审查任务中使用，只审查与交接，不修复业务。文档、配置、构建和实际测试另行核对。

## 内置与外部能力

- 按当前确认配置保留内置 `TRAE-security-review`，用于指定变更集的安全审查；未发现可报告漏洞不等于全项目安全。
- 内置 `TRAE-code-review` 保持关闭，使用项目适配副本，避免重复触发；`TRAE-debugger`、`TRAE-generate-mini-app` 暂不启用。
- 新增 MCP 或 Plugin 必须有具体能力缺口；Skill 是方法，MCP 是连接，Plugin 是分发。不要为覆盖术语或 star 数整套安装重复能力。

## 执行边界

- 技能描述和角色提示只是行为约束，不等于文件写入、终端或网络权限已强制隔离。配置与验证时核实实际工具和写入范围；不能把制度约束报告为已实现的安全隔离。
- 技能不授权删除已有实现、修改确认需求或验收标准、安装依赖、提交、推送、发布、对外发消息或自动派发角色。已明确授权的范围内可连续工作，无需重复申请。
- 同一问题连续两轮“开发提交修复—独立验证完成复测”仍失败，暂停该问题交用户判断；工具调用与假设实验不计轮次。无依赖且已授权的其他工作可继续。范围、验收、关键架构或预算变化立即升级。
- 业务问题与测试问题分别记录；不通过削弱断言或更改正确预期制造通过。真实模型、外部服务、真机与替身验证分开说明。
- 失败现场、截图、日志、真实性和敏感信息处理仍按公共规则执行。清理临时产物不能删除唯一的失败和修复证据。

## 加载、来源与验证

- 只按需读取技能正文与相关参考资料，不把九份正文全部注入公共上下文。技能引用已安装名称；没有兼容技能工具时实际读取对应文件，不能假装调用成功。
- 检查来源、正文、脚本、依赖、权限与网络目的地；固定版本，不静默升级。新版先隔离验证，再启用；保留旧版、差异和回滚路径。
- 分别记录目录发现、正确触发、正文读取、可观测上下文装配、真实行为与工具结果。文件哈希和关键词存在性不能证明模型遵守。
- 本机没有原始上下文观测入口时明确说明，不声称已证明全文注入。启用状态以实际设置为准；不设置统一独立 Agent 验证前置环节；在实际任务中观察触发、交接与执行，发现具体问题再修正。产品程序测试、独立复测与用户验收继续执行。
