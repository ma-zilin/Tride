## 1. 一页速查：需求分析十条硬标准

1. 先问问题与目标，再谈解决方案；不把"买某模型""上某技术"当成需求。
2. 每条需求都要能说明受益者与价值依据，否则无法排序、无法取舍。
3. 每条需求必须落在业务需求、用户需求、系统级需求三者之一，并能上下追溯。
4. 功能、非功能、领域三类需求都要检查，不能只写功能需求。
5. 非功能需求必须转成可度量指标：场景、负载、统计口径、阈值、验证方法。
6. 进入基线前过六道门：正确、一致、完整、可行、可验证、无歧义。
7. 用"条件—主体—行为—结果—度量"重写模糊句，清除"智能、快速、合适、及时"等不可验证措辞。
8. 必须写清失败、降级与人工接管规则，不能只写主成功路径。
9. 重大冲突必须显式记录：结论、依据、责任人、复审触发条件；不能用"全都保留"或"大家同意"掩盖。
10. AI 可以生成候选，不能替代业务价值判断，也不能替代对最终基线的责任。

## 2. 需求分析标准体系（提炼）

### 2.1 需求的定义与判断标准（PDF p.4）

- 需求是利益相关者为实现目标所需要的条件或能力，以及系统必须满足的、可被记录和验证的条件或能力。
- 需求起点是问题与目标，不是预设解决方案；"降低误派率"是业务问题，"必须购买某品牌模型"通常是方案约束，两者不能混为一谈。
- 需求必须有明确的受益者与价值依据；说不清谁因此改善，就难以判断优先级，也难以在冲突中取舍。
- 需求最终要成为设计、实现与测试的共同依据；"系统要快"只是期待，"查询在正常负载下 P95 响应时间不超过 2 秒"才具备验证条件。
- SRS 记录已达成共识的需求，但文档本身不等于全部需求工程活动。

**Agent 操作含义**

- 收到一句诉求，先拆出"问题/目标"与"候选方案"两层，方案不直接进需求条目。
- 每条需求必须能回答"谁受益、改善什么、如何验证"；答不上来的，标为待澄清，不写成确定需求。

### 2.2 层次标准：业务 / 用户 / 系统级（PDF p.5–7）

三层结构，越往上越关注价值，越往下越接近可实现、可验证的系统约定：

| 层次 | 关注点 | 回答的问题 |
|---|---|---|
| 业务需求 | 组织目标、投资理由与成功标准 | 为什么做 |
| 用户需求 | 角色、场景与任务 | 用户要完成什么 |
| 系统级需求 | 功能、质量属性、接口与约束 | 系统必须做到什么 |

关键约束：功能需求是系统级需求的重要组成部分，**不能把"功能需求"误当成与前两层并列的抽象层次**。

责任主体与确认方式：

| 层次 | 核心问题 | 主要表达 | 主要确认者 |
|---|---|---|---|
| 业务需求 | 为什么建设？ | 业务目标、范围、收益、成功指标 | 发起人、业务负责人 |
| 用户需求 | 用户要完成什么？ | 角色目标、任务场景、业务流程、用户故事 | 真实用户、业务代表 |
| 系统级需求 | 系统必须提供什么？ | 功能行为、外部接口、质量属性、设计约束 | 产品、研发、测试、运维 |
| 向下分解 | 如何逐步具体化？ | 目标分解为任务，任务分解为可验证系统能力 | 需求分析师组织 |
| 向上支撑 | 为何需要该能力？ | 每条系统需求应能回溯到用户任务与业务目标 | 评审组共同确认 |

**检查方法（课件原文）**：对每条系统级需求连续追问"它支持哪个用户任务、又支撑哪个业务目标"；找不到上层依据的需求可能是镀金需求，找不到下层实现的目标可能只是口号。

**常见错位（以"自动派单"为例）**

- 只写"使用大模型自动派单"：直接跳到方案，缺少业务成功标准。
- 只写"用户想减少工作"：没有定义具体任务、触发条件和系统响应。
- 只写"准确率高"：没有样本范围、计算口径、阈值和验收责任人。

**Agent 操作含义**

- 每条需求强制标注层次；系统级需求必须挂接用户任务与业务目标，形成双向追溯。
- 发现只有系统级描述而无上层依据时，先问"为什么"，不直接补写业务目标。

### 2.3 分类标准：功能 / 非功能 / 领域（PDF p.9–17）

分类依据是需求所描述的对象，而不是文档所在章节。

| 类别 | 定义 | 示例 |
|---|---|---|
| 功能需求 | 规定系统在特定条件下应提供的服务、处理的数据或作出的响应 | 系统应把人工确认后的工单分派给所选支持组并记录时间 |
| 非功能需求（NFR） | 规定质量属性、全局约束或运行条件，影响系统如何提供服务 | 在 500 并发用户下，工单查询 P95 响应时间 ≤ 2 秒 |
| 领域需求 | 源于特定业务领域的法规、术语、计算规则或业务惯例 | 高优先级故障必须按企业 SLA 规则在 15 分钟内升级 |

**功能需求写法（课件要点）**

- 完整行为包含触发、处理与结果；"当员工提交标题和描述时，系统应生成工单编号并进入待分派状态"比"支持创建工单"更易理解和测试。
- 必须覆盖主成功场景、替代路径与异常路径；除分类成功外，还要规定模型不可用、置信度不足、支持组停用时系统如何降级处理。
- 保持需求与设计分离；"提供相似工单检索"是需求，"使用某向量数据库并建立 HNSW 索引"是候选设计方案，除非它是外部强制约束。
- 使用稳定、统一的业务术语；"报修单""服务请求""工单"若指同一概念，应在术语表中选定首选词并全程一致。

**非功能需求写法（课件要点）**

- 非功能需求并非"非功能所以不重要"，它们常是架构显著型需求（Architecturally Significant Requirements / ASR）。
- 把主观形容词转成可测量指标："响应快"应转成特定负载、数据量和统计口径下的响应时间；"安全"应转成身份鉴别、授权、审计与保护规则。
- 质量属性之间存在权衡；更强加密会增加计算开销，更高可用性会增加冗余成本；需求评审应显式记录取舍理由。
- 全局 NFR 要分配到具体场景和组件；"系统可用性 99.9%"需进一步明确统计周期、计划维护是否排除、哪些关键服务纳入计算。
- AI 系统增加模型质量与治理指标；除性能和安全外，还要定义准确率、拒答阈值、偏差评估、可解释性和人工接管条件。

**领域需求写法（课件要点）**

- 领域术语规定概念边界；在 IT 服务管理中，"事件""服务请求""问题"含义不同，混用会导致分类、统计和 SLA 计算错误。
- 领域规则规定合法行为；例如账号权限工单必须由申请人直属负责人审批，系统不能因追求自动化而绕过授权链。
- 领域约束可能来自法规、标准或组织制度；分析师要记录规则来源、适用范围和版本，不能仅凭"大家一直这么做"固化过时流程。
- 领域需求需要领域专家确认；开发人员能检查技术一致性，但只有业务规则负责人能确认计算口径、例外条件与政策解释。

**三类需求的边界与常见误区**

正确拆分示例：

- 功能：系统应根据工单内容生成支持组候选列表。
- 非功能：候选生成服务 P95 响应时间 ≤ 800 ms。
- 领域：权限申请类工单必须路由到权限组并经过直属负责人审批。
- 三类需求分别映射到功能测试、性能测试和业务规则测试。

常见误区：

- 把"界面采用蓝色"一律称为非功能需求；它可能只是设计偏好。
- 把"使用 Python"称为功能需求；它描述实现技术而非用户可观察行为。
- 把领域规则藏在代码里不写入需求；规则变化时将无法追溯影响。
- 按"重要/不重要"区分功能与非功能；分类与重要性没有直接关系。

### 2.4 质量门禁：优秀需求的六大特征（PDF p.16–17）

| 特征 | 含义 |
|---|---|
| 正确 | 真实反映经授权利益相关者的需要，并符合适用业务规则 |
| 一致 | 与其他需求、术语、模型和约束不存在逻辑矛盾 |
| 完整 | 正常、异常、边界、数据和质量要求达到当前层次所需粒度 |
| 可行 | 在技术、成本、进度、资源和合规约束内能够实现 |
| 可验证 | 能通过检查、分析、演示或测试给出客观结论 |
| 无歧义 | 关键术语与量词只有一种合理解释，不依赖个人猜测 |

**评审检查表（课件原文）**

| 特征 | 评审问题 | 常见缺陷 | 修正动作 |
|---|---|---|---|
| 正确性 | 是否对应真实需要与有效规则？ | 分析师自行猜测需求 | 标注来源并由授权角色确认 |
| 一致性 | 是否与其他需求和术语冲突？ | 同一状态出现两种定义 | 统一术语并消解逻辑矛盾 |
| 完整性 | 是否覆盖触发、结果与例外？ | 只写正常流程 | 补充边界、异常、数据与 NFR |
| 可行性 | 资源与技术是否支撑？ | 目标超过数据和算力条件 | 开展 PoC 并记录约束与风险 |
| 可验证性 | 能否设计客观验收方法？ | 使用"快速、友好、智能"等词 | 补充场景、指标、阈值与口径 |
| 无歧义 | 是否只有一种合理解释？ | "及时""必要时""相关人员" | 定义术语、量词、角色和条件 |

评审纪律：评审者应依据证据给出"通过 / 修改 / 待确认"，而非凭感觉打分。

### 2.5 可验证写法标准（PDF p.18）

**四步重写**

1. 重写功能行为：写清触发、输入、处理、输出。示例：当员工提交标题与描述后，系统应返回网络组、桌面组、应用组、权限组、其他中的 Top-3 候选及置信度。
2. 重写质量要求：给出数据集、统计口径、阈值。示例：在约定测试集上，Top-1 分派准确率应不低于 90%；在线推理 P95 响应时间应不超过 800 ms。
3. 补充失败与接管规则：示例：最高置信度低于 0.60 或模型服务不可用时，系统应进入人工分派队列，不得静默自动派单。
4. 统一术语：同一概念只保留一个首选词，避免"报修单/服务请求/工单"混用。

**可执行的句式模板（提炼）**

> 在〔条件/负载/数据范围〕下，当〔触发事件〕发生时，〔系统/角色〕应〔可观察行为〕，输出〔结果〕，并在〔度量口径〕下满足〔阈值〕；若〔异常条件〕，则〔降级/接管/提示规则〕。

**模糊词黑名单（课件的反例归纳）**：智能、快速、合适、及时、必要时、相关人员、尽可能、尽量减少、高可用、准确率高、友好、易用（未给度量时）。

**标准引用纪律（课件原文）**：IEEE 830-1998 曾广泛用于 SRS 实践，但已被 ISO/IEC/IEEE 29148 系列标准取代；引用时应说明其历史地位，不把旧标准写成现行标准。

### 2.6 过程标准：需求工程五阶段（PDF p.20–28）

主流程：需求获取（Elicitation，发现来源与事实）→ 需求分析（Analysis，澄清、建模、协商）→ 需求规格（Specification，结构化表达）→ 需求验证（Validation，确认正确且可验）→ 需求管理（Management，基线、追溯、变更）。

课件明确：五阶段是逻辑活动，不是只能单向执行的瀑布步骤；验证发现问题会回到获取与分析；管理贯穿项目全周期。

| 阶段 | 核心目标 | 主要输入 | 代表性输出 |
|---|---|---|---|
| 需求获取 | 发现需求来源与真实问题 | 目标、现状材料、角色线索 | 原始需求、事实、假设、问题清单 |
| 需求分析 | 澄清、建模、协商与排序 | 原始需求与领域知识 | 分析模型、冲突结论、候选清单 |
| 需求规格 | 形成统一、结构化表达 | 已分析需求与模板规则 | SRS、用户故事、模型、验收标准 |
| 需求验证 | 检查质量并确认真实需要 | 候选规格与原型 | 缺陷清单、评审记录、批准结论 |
| 需求管理 | 控制状态、追溯与变化 | 需求及全部关联制品 | 基线、RTM、变更记录、状态报告 |

**阶段一：需求获取**

- 核心目标：覆盖真实来源并理解问题情境。不仅记录利益相关者说了什么，还要通过观察、数据和现有制度发现未被表达的隐性需求。
- 主要输入：业务目标、现状材料与利益相关者线索。材料包括流程制度、历史数据、旧系统、投诉记录和合规要求，需保留来源与版本。
- 关键任务：访谈、观察、工作坊、问卷、文档与接口分析。方法选择取决于问题类型；操作性知识适合现场观察，冲突性问题适合跨角色工作坊。
- 主要输出：原始需求、事实、假设与待澄清项。此时产物仍可矛盾或不完整，不能未经分析就直接承诺进入开发。

**阶段二：需求分析**

- 核心目标：澄清边界、结构与优先级。分析师识别重复、冲突、遗漏和不可行项，把零散表达组织为一致的问题模型。
- 关键任务：分类、建模、分解、协商与可行性初判。用业务流程、用例、领域概念与状态模型表达不同视角，模型必须与文本相互校验。
- 输入与输出的转换：输入是带来源的原始需求和事实；输出是边界明确、关系清晰、已初步排序的需求集合。
- 准出标准：重大冲突已记录处理结论。未解决的关键分歧必须作为风险或待决项显式存在，不能用模糊措辞掩盖。

**阶段三：需求规格**

- 核心目标：把共识固化为结构化、可追溯的规格。规格可采用 SRS、用户故事与验收标准、模型和接口契约的组合，不要求所有项目只有一种模板。
- 关键任务：编号、措辞、建模与组织文档。每条需求应有唯一标识、来源、优先级、版本和验收依据，以支持后续追踪。
- 控制抽象层次与设计泄漏：规格应说清外部可观察结果；只有真正强制的技术、法规或兼容约束才应写成设计约束。
- 主要输出：候选需求基线。"候选"意味着还需经过验证与授权审批，文档完成不代表需求已经正确。

**阶段四：需求验证**

- 验证关注规格质量：检查每条需求是否正确、一致、完整、可行、可验证、无歧义，并核对模型与文本。
- 确认关注真实需要：让业务与用户判断"这是否解决我们的实际问题"，避免形式正确却方向错误。
- 常用方法：评审、原型、场景走查与测试设计。若无法为需求设计验收测试，往往说明条件、结果或质量阈值仍不清楚。
- 主要输出：问题清单、修订记录与批准结论。只有满足通过标准并获得授权确认的版本，才可建立需求基线。

**阶段五：需求管理**

- 核心目标：维护状态、版本、优先级和追溯关系。团队应随时知道需求当前由谁负责、在哪个版本实现、验证结果如何，以及与哪些制品相关。
- 关键任务：基线、追溯、变更、配置与状态报告。需求管理不是项目末期的文档整理，而是在第一条需求出现时就开始。
- 管理的对象包括需求及其决策依据：除了正文，还应保留来源、讨论结论、拒绝理由、影响分析和审批记录。
- 管理成功的标志是"变化可解释"：不是追求零变更，而是让每次变更都能回答为何改、影响谁、谁批准、如何验证。

### 2.7 利益相关者标准（PDF p.29–35）

**定义**：利益相关者（Stakeholder）是能够影响系统、被系统影响，或认为自己会被影响的个人、群体或组织。

**识别：从业务链、生命周期和风险责任出发**

- 不能只列"客户和用户"，还要覆盖运营、运维、安全、采购、审计、外部服务方及被间接影响群体。
- AI 系统会进一步扩大范围：数据提供方、标注团队、模型审计方和伦理合规岗会直接影响数据质量、模型边界与上线资格。

**系统化识别五步法**

1. 从目标找责任者：识别项目发起人、业务目标负责人和预算决策者，确认谁对业务结果负责。
2. 沿业务流程找参与者：逐环节识别发起、处理、审批、接收结果和处理异常的角色，覆盖一线真实用户。
3. 沿系统边界找协作者：检查上下游系统、外部接口、供应商、数据来源方和运维团队，识别依赖关系。
4. 沿风险责任找监督者：纳入安全、隐私、法务、审计和质量负责人，确认谁对事故与违规承担责任。
5. 滚雪球复核：每次访谈都询问"还有谁受影响或掌握关键信息"，直到新增角色和诉求趋于稳定。

**分类：多维分类补齐视角，再决定参与方式**

| 分类维度 | 典型类别 | 分析价值 | 注意事项 |
|---|---|---|---|
| 组织边界 | 内部 / 外部 | 识别合同、接口和责任边界 | 外部角色也可能拥有高决策权 |
| 影响程度 | 核心 / 边缘 | 安排访谈深度与参与频率 | 边缘角色可能暴露关键例外 |
| 使用关系 | 直接用户 / 间接受影响者 | 覆盖实际操作与社会影响 | 非用户不等于无诉求 |
| 生命周期 | 建设 / 运行 / 审计 / 退役 | 覆盖全生命周期要求 | 不能只关注上线前角色 |
| 态度 | 支持 / 中立 / 抵触 | 提前设计沟通与采纳策略 | 态度会变化，需要持续更新 |

课件强调：分类帮助安排参与方式，但不能据此断言某类角色的诉求天然更重要；分类不是贴标签。

**识别之后的分析四问**

- 诉求：角色希望系统带来什么变化。调度员关注减负和可控，管理者关注效率与数据，一线运维关注派单质量和责任边界。
- 贡献：角色能提供什么知识或资源。真实用户提供操作细节，运维提供异常经验，数据团队提供标签质量，法务提供合规解释。
- 影响力：角色能否改变范围、预算或上线决策。影响力高不等于需求一定正确，但意味着必须更早、更充分地达成共识。
- 风险与态度：角色可能如何推动或阻碍项目。对自动派单抵触的一线人员若长期缺席，系统即使技术达标也可能因不采纳而失败。

**权力—利益矩阵**

|  | 低利益 | 高利益 |
|---|---|---|
| **高权力** | 适时告知：关注关键节点与决策影响 | 重点关注：深度参与并共同决策 |
| **低权力** | 最小化管理：监测变化并提供基本信息 | 保持沟通：持续收集体验与反馈 |

矩阵是沟通资源配置工具，不是给角色排"尊卑"；象限位置会随项目阶段、责任变化和事件发生而调整。

### 2.8 协商与确认标准（PDF p.35–37）

- 协商解决"存在分歧怎么办"，确认解决"我们理解的是不是同一件事"，正式评审则把共识固化为可追责的基线。
- 需求协商围绕目标、证据与约束寻找可接受方案；协商不等于谁声音大听谁的，也不等于把冲突需求全部保留，而是透明记录取舍。
- 需求确认让利益相关者看见并核实预期系统；原型适合确认交互和流程，文档评审适合逐条确认规则、接口、质量与异常。
- 需求评审用角色、材料、准入和准出标准保障严肃性；评审结论应形成问题责任人、完成期限、复核证据和批准记录。

**三项原则（先对齐问题，再讨论方案）**

1. 双赢原则：识别各方底层利益而非只盯立场。例如管理者要效率、一线要可控，可用"AI 建议 + 人工确认"兼顾。
2. 优先级导向原则：在资源约束下围绕价值、风险和依赖排序。不承诺"全都做"，而是明确先做什么、延期什么以及代价。
3. 目标对齐原则：以已确认业务目标和成功标准作为共同裁判。当个人偏好冲突时，优先选择更能支撑目标且证据更充分的方案。

**五步流程**：分歧识别（定位冲突对象与影响）→ 诉求澄清（区分立场、利益和约束）→ 方案共创（形成可比较候选方案）→ 权衡评估（价值—成本—风险—依赖）→ 共识达成（记录结论、条件与异议）。

协商结论不是一句"大家同意"，而应包含：被选方案、未选方案、判断依据、适用条件、责任人、复审触发条件。

### 2.9 AI 赋能的边界（仅依据本 PDF 可确认的内容）

- 章节摘要：大模型生成候选成果，人依据业务证据作价值判断并对最终基线负责。
- AI 系统扩大利益相关者范围：数据提供方、标注团队、模型审计方、伦理合规岗。
- AI 系统需增加模型质量与治理指标：准确率、拒答阈值、偏差评估、可解释性、人工接管条件。
- 本 PDF 未给出提示词、模型选型、AI 工作流或自动评审方法，本文不补写。

## 3. 需求分析 Agent 操作手册（提炼）

### 3.1 输入准入检查

开始分析前确认：

- [ ] 是否拿到业务目标与成功标准（没有则标为待澄清，不自行编造）。
- [ ] 是否知道需求来源、原始表述与提供者。
- [ ] 是否区分了问题/目标与候选方案。
- [ ] 是否识别了主要利益相关者，而不只是"客户和用户"。
- [ ] 是否知道当前处于五阶段的哪个阶段，以及本阶段准出标准。

### 3.2 过程中必须产出的中间物

- 原始需求清单：原文、来源、事实/假设/待澄清标记。
- 层次与分类标注：业务/用户/系统级；功能/非功能/领域。
- 冲突与遗漏清单：冲突对象、各方立场与底层利益、处理结论或待决状态。
- 利益相关者表：角色、诉求、贡献、影响力、风险与态度、参与策略。
- 术语表：概念、首选词、禁用同义词、定义来源。
- 可验证化前后的对照：模糊原句 → 重写句 → 验收方法。

### 3.3 输出自检清单

逐条检查，任一不满足则不得标记为"已确认需求"：

- [ ] 每条需求有唯一编号、来源、层次、类型、优先级、状态。
- [ ] 每条系统级需求能回溯到用户任务与业务目标。
- [ ] 每条需求有受益者与价值依据。
- [ ] 功能需求写清触发、处理、结果、替代路径、异常路径。
- [ ] 非功能需求写清场景、负载、统计口径、阈值、验证方法。
- [ ] 领域需求记录了规则来源、适用范围、版本，并经领域专家确认。
- [ ] 已清除模糊词；无法量化的已标为待澄清，而不是勉强通过。
- [ ] 已写失败、降级与人工接管规则。
- [ ] 六特征逐项有证据结论（通过/修改/待确认），不是凭感觉。
- [ ] 重大冲突有结论、依据、责任人、复审触发条件。
- [ ] 文档状态是"候选基线"，未经授权不宣称已批准。

### 3.4 禁止行为

- 不编造来源、访谈记录、数据或用户原话。
- 不把假设写成事实；假设必须单独列出并标注验证方式。
- 不用形容词替代阈值；不把"快速、智能、及时、合适"直接写进验收标准。
- 不替用户做价值取舍；涉及范围、优先级、合规冲突时提交用户判断。
- 不把实现方案写成需求；只有外部强制约束才可写入设计约束。
- 不把"文档写完"等同于"需求正确"。
- 不以"AI 生成"为由跳过评审与授权确认。

### 3.5 需求条目建议字段（与现有基线兼容）

| 字段 | 说明 |
|---|---|
| 编号 | 沿用项目现有 FR/NFR/AC/BR/D/OD 体系 |
| 标题 | 一句话可识别 |
| 层次 | 业务 / 用户 / 系统级 |

- 定义框：需求工程（Requirements Engineering / RE）不是"写一份文档"，而是围绕需求发现、澄清、表达、验证与演化开展的一组持续活动。

  - 通过利益相关者分析、需求协商、需求确认与可行性研判，避免只听见最强势角色而遗漏真实用户。
- 全程管理：让变化可评估、可审批、可追溯

- AI 赋能：提升信息处理效率而不让渡责任
  - 大模型生成候选成果，人依据业务证据作价值判断并对最终基线负责。

### PDF p.3 / 内部第 6 页：2.1 需求工程核心体系

副标题：本节知识地图

- 提示框：判断一个需求是否值得进入开发，至少要回答四个问题：处于哪个层次、属于哪类需求、质量是否合格、处于工程流程的哪个阶段。
- 2.1.1 需求的定义与层次划分
  - 业务需求说明组织为何投入，用户需求说明角色要完成什么任务，系统级需求规定系统必须提供什么能力与质量。
- 2.1.2 需求的三大分类
  - 功能需求定义行为，非功能需求定义质量与约束，领域需求来自业务领域的规则和知识。
- 2.1.3 优秀需求的六大特征
  - 正确、一致、完整、可行、可验证、无歧义是进入基线前的共同质量门槛。
- 2.1.4 需求工程五阶段
  - 获取、分析、规格、验证、管理不是一次性流水线，而是持续反馈、逐步收敛的活动体系。

### PDF p.4 / 内部第 7 页：需求到底是什么？

副标题：从"愿望"到"可验证约定"

- 定义框：需求是利益相关者为实现目标所需要的条件或能力，以及系统必须满足的、可被记录和验证的条件或能力。
- 需求起点是问题与目标，而不是预设解决方案
  - "降低误派率"表达业务问题；"必须购买某品牌模型"通常是方案约束，二者不能混为一谈。
- 需求必须有明确的受益者与价值依据
  - 若无法说明谁因该需求获得何种改善，就难以判断其优先级，也难以在冲突时做取舍。
- 需求最终要能成为设计、实现与测试的共同依据
  - "系统要快"只是期待；"查询在正常负载下 P95 响应时间不超过 2 秒"才具备验证条件。
- 需求规格说明（Software Requirements Specification / SRS）记录已达成共识的需求，但文档本身不等于全部需求工程活动。

### PDF p.5 / 内部第 8 页：需求层次金字塔

副标题：越向上越关注价值，越向下越接近可实现与可验证的系统约定

- 业务需求 Business Requirements：组织目标、投资理由与成功标准；为什么做
- 用户需求 User Requirements：角色、场景与任务；用户要完成什么
- 系统级需求 System-level Requirements：功能、质量属性、接口与约束；系统必须做到什么
- 提示框：本章采用"业务需求—用户需求—系统级需求"三层结构；功能需求属于系统级需求的重要组成部分，不能把"功能需求"误当成与前两层并列的抽象层次。

### PDF p.6 / 内部第 9 页：三个需求层次：关注点与责任主体

副标题：同一句话放错层次，会导致目标、任务与系统行为相互混淆

| 层次 | 核心问题 | 主要表达 | 主要确认者 |
|---|---|---|---|
| 业务需求 | 为什么建设？ | 业务目标、范围、收益、成功指标 | 发起人、业务负责人 |
| 用户需求 | 用户要完成什么？ | 角色目标、任务场景、业务流程、用户故事 | 真实用户、业务代表 |
| 系统级需求 | 系统必须提供什么？ | 功能行为、外部接口、质量属性、设计约束 | 产品、研发、测试、运维 |
| 向下分解 | 如何逐步具体化？ | 目标分解为任务，任务分解为可验证系统能力 | 需求分析师组织 |
| 向上支撑 | 为何需要该能力？ | 每条系统需求应能回溯到用户任务与业务目标 | 评审组共同确认 |

### PDF p.7 / 内部第 10 页：层次错位：一句"自动派单"如何逐层澄清

副标题：先问价值，再问任务，最后定义系统能力
标签：贯穿案例 · 2.1 需求层次

**自顶向下分解**

- 业务需求：将人工误派造成的二次流转显著降低，支撑首次响应中位数 ≤ 1.5 小时。
- 用户需求：调度员查看分类建议与依据，确认或改派到网络组、桌面组、应用组、权限组或其他。
- 系统需求：接收标题与描述后输出 Top-3 支持组、置信度和可解释依据；低置信度进入人工队列。

**常见错位**

- 只写"使用大模型自动派单"：直接跳到方案，缺少业务成功标准。
- 只写"用户想减少工作"：没有定义具体任务、触发条件和系统响应。
- 只写"准确率高"：没有样本范围、计算口径、阈值和验收责任人。

**检查方法**

- 对每条系统级需求连续追问"它支持哪个用户任务、又支撑哪个业务目标"；找不到上层依据的需求可能是镀金需求，找不到下层实现的目标可能只是口号。

### PDF p.8 / 内部第 11 页：单选题

题干：某项目写道："为降低工单二次流转造成的等待，一期上线后首次响应中位数应不超过 1.5 小时。"该表述主要属于哪个需求层次？

- A. 业务需求
- B. 用户需求
- C. 系统功能需求
- D. 数据库设计约束

课件高亮答案：A（业务需求）。

### PDF p.9 / 内部第 12 页：需求的三大分类

副标题：分类依据是需求所描述的对象，而不是文档所在章节

- 功能需求 Functional Requirement
  - 规定系统在特定条件下应提供的服务、处理的数据或作出的响应。
  - 示例：系统应把人工确认后的工单分派给所选支持组并记录时间。
- 非功能需求 Non-functional Requirement / NFR
  - 规定质量属性、全局约束或运行条件，影响系统如何提供服务。
  - 示例：在 500 并发用户下，工单查询 P95 响应时间 ≤ 2 秒。
- 领域需求 Domain Requirement
  - 源于特定业务领域的法规、术语、计算规则或业务惯例。
  - 示例：高优先级故障必须按企业 SLA 规则在 15 分钟内升级。

### PDF p.10 / 内部第 13 页：功能需求：定义可观察的系统行为

副标题：回答"系统做什么"

- 完整行为包含触发、处理与结果
  - "当员工提交标题和描述时，系统应生成工单编号并进入待分派状态"比"支持创建工单"更易理解和测试。
- 必须覆盖主成功场景、替代路径与异常路径
  - 除了分类成功，还应规定模型不可用、置信度不足、支持组停用时系统如何降级处理。
- 保持需求与设计分离
  - "提供相似工单检索"是需求；"使用某向量数据库并建立 HNSW 索引"是候选设计方案，除非它是外部强制约束。
- 使用稳定、统一的业务术语
  - 若"报修单""服务请求""工单"指同一概念，应在术语表中选定一个首选词并全程一致。

### PDF p.11 / 内部第 14 页：非功能需求：决定系统"做得怎样"

副标题：质量属性常常比功能清单更早决定架构

- 定义框：非功能需求并非"非功能所以不重要"，它们常是架构显著型需求（Architecturally Significant Requirements / ASR）。
- 把主观形容词转成可测量指标
  - "响应快"应转成特定负载、数据量和统计口径下的响应时间；"安全"应转成身份鉴别、授权、审计与保护规则。
- 质量属性之间存在权衡
  - 更强加密会增加计算开销，更高可用性会增加冗余成本；需求评审应显式记录取舍理由。
- 全局 NFR 要分配到具体场景和组件
  - "系统可用性 99.9%"需进一步明确统计周期、计划维护是否排除、哪些关键服务纳入计算。
- AI 系统增加模型质量与治理指标
  - 除性能和安全外，还要定义准确率、拒答阈值、偏差评估、可解释性和人工接管条件。

### PDF p.12 / 内部第 15 页：非功能需求常见维度与度量指标对照表

副标题：度量必须同时写明场景、阈值、统计口径与验证方式

| 维度 | 关注问题 | 可度量指标 | 智工单示例 |
|---|---|---|---|
| 性能 | 响应是否及时 | P95/P99 响应时间、吞吐量 | 500 并发下查询 P95 ≤ 2 秒 |
| 可用性 | 服务能否持续提供 | 可用率、RTO、RPO | 月可用率 ≥ 99.9%，RTO ≤ 30 分钟 |
| 安全性 | 访问与数据是否受控 | 越权用例通过率、审计覆盖率 | 全部敏感操作留审计日志 |
| 易用性 | 用户能否正确高效完成任务 | 任务成功率、平均操作步数 | 新用户首次提交成功率 ≥ 95% |
| 可维护性 | 修改与定位是否高效 | 修复时长、模块耦合、覆盖率 | 关键规则具备自动化回归测试 |
| 可扩展性 | 负载增长时能否扩容 | 扩容时间、容量上限 | 工单量翻倍时可水平扩容 |
| 模型质量 | AI 输出是否可靠 | 准确率、召回率、拒答率 | 五分类人工复核准确率 ≥ 90% |
| 公平与隐私 | 是否产生不当差异或泄露 | 群体差异、脱敏覆盖率 | 工号与手机号进入模型前 100% 脱敏 |

### PDF p.13 / 内部第 16 页：领域需求：把"行话与规则"转成系统约束

副标题：回答"这个领域有什么不能忽略的知识"

- 领域术语规定概念边界
  - 在 IT 服务管理中，"事件""服务请求""问题"含义不同；混用会导致分类、统计和 SLA 计算错误。
- 领域规则规定合法行为
  - 例如账号权限工单必须由申请人直属负责人审批，系统不能因追求自动化而绕过授权链。
- 领域约束可能来自法规、标准或组织制度
  - 分析师要记录规则来源、适用范围和版本，不能仅凭"大家一直这么做"固化过时流程。
- 领域需求需要领域专家确认
  - 开发人员能检查技术一致性，但只有业务规则负责人能确认计算口径、例外条件与政策解释。

### PDF p.14 / 内部第 17 页：三类需求的边界：容易混淆的表达

副标题：同一业务目标可能同时派生出功能、质量与领域约束

**正确拆分**

- 功能：系统应根据工单内容生成支持组候选列表。
- 非功能：候选生成服务 P95 响应时间 ≤ 800 ms。
- 领域：权限申请类工单必须路由到权限组并经过直属负责人审批。
- 三类需求分别映射到功能测试、性能测试和业务规则测试。

**常见误区**

- 把"界面采用蓝色"一律称为非功能需求；它可能只是设计偏好。
- 把"使用 Python"称为功能需求；它描述实现技术而非用户可观察行为。
- 把领域规则藏在代码里不写入需求；规则变化时将无法追溯影响。
- 按"重要/不重要"区分功能与非功能；分类与重要性没有直接关系。

- A. 增加更多形容词以体现重要性
- B. 删除"99.9%"，改成"高可用"

### PDF p.16 / 内部第 19 页：优秀需求的六大核心特征

副标题：进入需求基线前的质量标尺

- 正确 + 一致
  - 正确：真实反映经授权利益相关者的需要，并符合适用业务规则。
  - 一致：与其他需求、术语、模型和约束不存在逻辑矛盾。
- 完整 + 可行
  - 完整：正常、异常、边界、数据和质量要求达到当前层次所需粒度。
  - 可行：在技术、成本、进度、资源和合规约束内能够实现。
- 可验证 + 无歧义
  - 可验证：能通过检查、分析、演示或测试给出客观结论。
  - 无歧义：关键术语与量词只有一种合理解释，不依赖个人猜测。

### PDF p.17 / 内部第 20 页：优秀需求六大特征评审检查表

副标题：评审者应依据证据给出"通过 / 修改 / 待确认"，而非凭感觉打分

| 特征 | 评审问题 | 常见缺陷 | 修正动作 |
|---|---|---|---|
| 正确性 | 是否对应真实需要与有效规则？ | 分析师自行猜测需求 | 标注来源并由授权角色确认 |
| 一致性 | 是否与其他需求和术语冲突？ | 同一状态出现两种定义 | 统一术语并消解逻辑矛盾 |
| 完整性 | 是否覆盖触发、结果与例外？ | 只写正常流程 | 补充边界、异常、数据与 NFR |
| 可行性 | 资源与技术是否支撑？ | 目标超过数据和算力条件 | 开展 PoC 并记录约束与风险 |
| 可验证性 | 能否设计客观验收方法？ | 使用"快速、友好、智能"等词 | 补充场景、指标、阈值与口径 |
| 无歧义 | 是否只有一种合理解释？ | "及时""必要时""相关人员" | 定义术语、量词、角色和条件 |

### PDF p.18 / 内部第 21 页：从模糊句到可验证需求

副标题：用"条件—主体—行为—结果—度量"重写

- 原句：系统应智能、快速地把工单分给合适的人
  - 问题在于"智能""快速""合适"均无统一判定标准，无法据此设计测试或确定责任。
- 重写功能行为
  - 当员工提交标题与描述后，系统应返回网络组、桌面组、应用组、权限组、其他中的 Top-3 候选及置信度。
- 重写质量要求
  - 在约定测试集上，Top-1 分派准确率应不低于 90%；在线推理 P95 响应时间应不超过 800 ms。
- 补充失败与接管规则
  - 最高置信度低于 0.60 或模型服务不可用时，系统应进入人工分派队列，不得静默自动派单。
- 注：IEEE 830-1998 曾广泛用于 SRS 实践，但已被 ISO/IEC/IEEE 29148 系列标准取代；引用时应说明其历史地位，不把旧标准写成现行标准。

### PDF p.20 / 内部第 23 页：需求工程五阶段流程图

副标题：获取—分析—规格—验证—管理：主流程与反馈闭环

- 需求获取 Elicitation：发现来源与事实
- 需求分析 Analysis：澄清、建模、协商
- 需求规格 Specification：结构化表达
- 需求验证 Validation：确认正确且可验
- 需求管理 Management：基线、追溯、变更
- 提示框：五阶段是逻辑活动，不是只能单向执行的瀑布步骤；验证发现问题会回到获取与分析；管理贯穿项目全周期。

### PDF p.21 / 内部第 24 页：阶段一：需求获取

副标题：Requirements Elicitation——发现而非抄录

- 核心目标：覆盖真实来源并理解问题情境
  - 不仅记录利益相关者说了什么，还要通过观察、数据和现有制度发现未被表达的隐性需求。
- 主要输入：业务目标、现状材料与利益相关者线索
  - 材料包括流程制度、历史数据、旧系统、投诉记录和合规要求，需保留来源与版本。
- 关键任务：访谈、观察、工作坊、问卷、文档与接口分析
  - 方法选择取决于问题类型；操作性知识适合现场观察，冲突性问题适合跨角色工作坊。
- 主要输出：原始需求、事实、假设与待澄清项
  - 此时产物仍可矛盾或不完整，不能未经分析就直接承诺进入开发。

### PDF p.22 / 内部第 25 页：阶段二：需求分析

副标题：Requirements Analysis——从材料到结构化理解

- 核心目标：澄清边界、结构与优先级
  - 分析师识别重复、冲突、遗漏和不可行项，把零散表达组织为一致的问题模型。
- 关键任务：分类、建模、分解、协商与可行性初判
  - 用业务流程、用例、领域概念与状态模型表达不同视角，模型必须与文本相互校验。
- 输入与输出的转换
  - 输入是带来源的原始需求和事实；输出是边界明确、关系清晰、已初步排序的需求集合。
- 准出标准：重大冲突已记录处理结论
  - 未解决的关键分歧必须作为风险或待决项显式存在，不能用模糊措辞掩盖。

### PDF p.23 / 内部第 26 页：阶段三：需求规格

副标题：Requirements Specification——形成统一、可沟通的表达

- 核心目标：把共识固化为结构化、可追溯的规格
  - 规格可采用 SRS、用户故事与验收标准、模型和接口契约的组合，不要求所有项目只有一种模板。
- 关键任务：编号、措辞、建模与组织文档
  - 每条需求应有唯一标识、来源、优先级、版本和验收依据，以支持后续追踪。
- 控制抽象层次与设计泄漏
  - 规格应说清外部可观察结果；只有真正强制的技术、法规或兼容约束才应写成设计约束。
- 主要输出：候选需求基线
  - "候选"意味着还需经过验证与授权审批，文档完成不代表需求已经正确。

### PDF p.24 / 内部第 27 页：阶段四：需求验证

副标题：Requirements Validation——确认"写对了"也"写的是对的"

- 验证关注规格质量
  - 检查每条需求是否正确、一致、完整、可行、可验证、无歧义，并核对模型与文本。
- 确认关注真实需要
  - 让业务与用户判断"这是否解决我们的实际问题"，避免形式正确却方向错误。
- 常用方法：评审、原型、场景走查与测试设计
  - 若无法为需求设计验收测试，往往说明条件、结果或质量阈值仍不清楚。
- 主要输出：问题清单、修订记录与批准结论
  - 只有满足通过标准并获得授权确认的版本，才可建立需求基线。

### PDF p.25 / 内部第 28 页：阶段五：需求管理

副标题：Requirements Management——让需求演化保持受控

- 核心目标：维护状态、版本、优先级和追溯关系
  - 团队应随时知道需求当前由谁负责、在哪个版本实现、验证结果如何，以及与哪些制品相关。
- 关键任务：基线、追溯、变更、配置与状态报告
  - 需求管理不是项目末期的文档整理，而是在第一条需求出现时就开始。
- 管理的对象包括需求及其决策依据
  - 除了正文，还应保留来源、讨论结论、拒绝理由、影响分析和审批记录。
- 管理成功的标志是"变化可解释"
  - 不是追求零变更，而是让每次变更都能回答为何改、影响谁、谁批准、如何验证。

副标题：用交付物和准出条件检查阶段是否真正完成

| 阶段 | 核心目标 | 主要输入 | 代表性输出 |
|---|---|---|---|

| 需求分析 | 澄清、建模、协商与排序 | 原始需求与领域知识 | 分析模型、冲突结论、候选清单 |
| 需求规格 | 形成统一、结构化表达 | 已分析需求与模板规则 | SRS、用户故事、模型、验收标准 |

- 环形结构：获取（发现事实）→ 分析（建模协商）→ 规格（统一表达）→ 验证（反馈纠偏）→ 管理（控制演化）→ 回到获取

### PDF p.29 / 内部第 32 页：2.2 利益相关者分析

副标题：谁受影响、谁有决策权、谁掌握关键知识

- 定义框：利益相关者（Stakeholder）是能够影响系统、被系统影响，或认为自己会被影响的个人、群体或组织。
- 识别：从业务链、生命周期和风险责任出发
  - 不能只列"客户和用户"，还要覆盖运营、运维、安全、采购、审计、外部服务方及被间接影响群体。
- 分类：内部/外部、核心/边缘只是描述视角
  - 分类帮助安排参与方式，但不能据此断言某类角色的诉求天然更重要。
- 管理：根据权力与利益制定差异化策略
  - 高权力角色影响决策，高利益角色承受使用结果；沟通频率、深度和渠道应有所不同。
- AI 系统：利益相关者范围继续扩展
  - 数据提供方、标注团队、模型审计方和伦理合规岗会直接影响数据质量、模型边界与上线资格。

### PDF p.30 / 内部第 33 页：系统化识别利益相关者的五步法

副标题：避免"只访谈最容易找到的人"

- STEP 1 从目标找责任者
  - 识别项目发起人、业务目标负责人和预算决策者，确认谁对业务结果负责。
- STEP 2 沿业务流程找参与者
  - 逐环节识别发起、处理、审批、接收结果和处理异常的角色，覆盖一线真实用户。
- STEP 3 沿系统边界找协作者
  - 检查上下游系统、外部接口、供应商、数据来源方和运维团队，识别依赖关系。
- STEP 4 沿风险责任找监督者
  - 纳入安全、隐私、法务、审计和质量负责人，确认谁对事故与违规承担责任。
- STEP 5 滚雪球复核
  - 每次访谈都询问"还有谁受影响或掌握关键信息"，直到新增角色和诉求趋于稳定。

### PDF p.31 / 内部第 34 页：利益相关者分类不是贴标签

副标题：用多维分类补齐视角，再决定参与方式

| 分类维度 | 典型类别 | 分析价值 | 注意事项 |
|---|---|---|---|
| 组织边界 | 内部 / 外部 | 识别合同、接口和责任边界 | 外部角色也可能拥有高决策权 |
| 影响程度 | 核心 / 边缘 | 安排访谈深度与参与频率 | 边缘角色可能暴露关键例外 |
| 使用关系 | 直接用户 / 间接受影响者 | 覆盖实际操作与社会影响 | 非用户不等于无诉求 |
| 生命周期 | 建设 / 运行 / 审计 / 退役 | 覆盖全生命周期要求 | 不能只关注上线前角色 |
| 态度 | 支持 / 中立 / 抵触 | 提前设计沟通与采纳策略 | 态度会变化，需要持续更新 |

### PDF p.32 / 内部第 35 页：识别之后还要分析什么？

副标题：从名单走向可执行的参与计划

- 诉求：角色希望系统带来什么变化
  - 调度员关注减负和可控，管理者关注效率与数据，一线运维关注派单质量和责任边界。
- 贡献：角色能提供什么知识或资源
  - 真实用户提供操作细节，运维提供异常经验，数据团队提供标签质量，法务提供合规解释。
- 影响力：角色能否改变范围、预算或上线决策
  - 影响力高不等于需求一定正确，但意味着必须更早、更充分地达成共识。
- 风险与态度：角色可能如何推动或阻碍项目
  - 对自动派单抵触的一线人员若长期缺席，系统即使技术达标也可能因不采纳而失败。

### PDF p.33 / 内部第 36 页：权力—利益矩阵四象限图

副标题：横轴为利益程度，纵轴为权力大小

- 高权力·低利益：适时告知——关注关键节点与决策影响
- 高权力·高利益：重点关注——深度参与并共同决策
- 低权力·低利益：最小化管理——监测变化并提供基本信息
- 低权力·高利益：保持沟通——持续收集体验与反馈
- 注：横轴 — 利益：低 → 高；纵轴 — 权力：低 → 高
- 提示框：矩阵是沟通资源配置工具，不是给角色排"尊卑"；象限位置会随项目阶段、责任变化和事件发生而调整。

### PDF p.34 / 内部第 37 页：单选题

题干：某系统要求"审计日志至少保留 180 天，且任何删除操作必须留痕"。某一线运维团队提出"保留 30 天即可，否则存储压力太大"。按本章方法，最合适的处理是？

- A. 直接采纳运维意见，因为他们是实际使用者
- B. 忽略运维意见，因为审计要求属于合规要求
- C. 记录冲突，补充法规/制度依据并组织相关方协商，形成决策
- D. 把两种要求都写进需求，交给开发决定

课件高亮答案：C。

### PDF p.35 / 内部第 42 页：2.3 需求协商与需求确认

副标题：从"各说各话"走向可执行、可签署的共识

- 定义框：协商解决"存在分歧怎么办"，确认解决"我们理解的是不是同一件事"，正式评审则把共识固化为可追责的基线。
- 需求协商：围绕目标、证据与约束寻找可接受方案
  - 协商不等于谁声音大听谁的，也不等于把冲突需求全部保留，而是透明记录取舍。
- 需求确认：让利益相关者看见并核实预期系统
  - 原型适合确认交互和流程，文档评审适合逐条确认规则、接口、质量与异常。
- 需求评审：用角色、材料、准入和准出标准保障严肃性
  - 评审结论应形成问题责任人、完成期限、复核证据和批准记录。

### PDF p.36 / 内部第 43 页：需求协商的三项原则

副标题：先对齐问题，再讨论方案

- 双赢原则
  - 识别各方底层利益而非只盯立场。例如管理者要效率、一线要可控，可用"AI 建议 + 人工确认"兼顾。
- 优先级导向原则
  - 在资源约束下围绕价值、风险和依赖排序。不承诺"全都做"，而是明确先做什么、延期什么以及代价。
- 目标对齐原则
  - 以已确认业务目标和成功标准作为共同裁判。当个人偏好冲突时，优先选择更能支撑目标且证据更充分的方案。

### PDF p.37 / 内部第 44 页：需求协商的完整流程

副标题：分歧识别 → 诉求澄清 → 方案共创 → 共识达成

- 分歧识别：定位冲突对象与影响
- 诉求澄清：区分立场、利益和约束
- 方案共创：形成可比较候选方案
- 权衡评估：价值-成本-风险-依赖
- 共识达成：记录结论、条件与异议
- 提示框：协商结论不是一句"大家同意"，而应包含被选方案、未选方案、判断依据、适用条件、责任人和复审触发条件。
