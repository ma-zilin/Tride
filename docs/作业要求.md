# 生成式人工智能应用基础二课后作业要求及评分标准

## 一、作业内容
自定义一个软件开发项目，使用TRAE与DeepSeek API完成需求分析、方案设计、代码开发、调试测试和产品验收。项目可以是网站、桌面端软件、小程序、手机端软件或其他类型的软件，不限制开发语言和框架。项目应具有明确的使用场景和能够实际演示的核心功能，范围适当，避免只有静态界面、缺少实际功能。

本次作业占课程总成绩60分。重点评价完整的开发流程、AI协作过程，以及遇到AI无法完成目标时，你如何分析问题、调整方案、采取措施并验证最终结果。

## 二、工具使用要求
1. 使用TRAE作为主要AI辅助开发工具，结合DeepSeek API开展项目开发，并在报告中说明二者的使用方式。
2. 提供能够证明TRAE与DeepSeek API实际使用情况的截图或调用记录，说明模型名称及相关配置，隐藏API密钥等敏感信息。
3. 如开发过程中使用其他辅助工具，应如实说明其用途及完成的工作。
4. 不要求最终软件本身具有AI功能；TRAE与DeepSeek API的使用要求针对本次开发过程。

## 三、项目开发要求
1. **明确需求和验收目标**
开发前说明项目面向哪些用户、解决什么问题、计划完成哪些功能，并列出可检查的验收标准。
验收标准应具体，例如“用户提交表单时显示错误提示”“关闭并重新打开软件后仍能读取已保存的数据”，不能只写“界面美观”“运行正常”。
如开发中调整需求，应记录调整原因、调整内容及其对最终目标的影响，不得通过删除失败功能来隐去问题。

2. **记录完整开发流程**
报告应覆盖以下阶段：
需求分析 → 方案设计 → 初始实现 → 功能迭代 → 调试与测试 → 最终验收。
记录各阶段的主要操作、使用AI完成的工作、你作出的判断和修改，以及阶段性结果。

3. **重点记录AI未达成目标时的处理过程**
对开发中出现的AI未能完成要求、生成结果错误、修复无效、功能不完整等情况，逐项说明：
- 原本希望AI完成什么。
- 实际产生了什么结果，与目标有何差距。
- 你如何发现问题，有哪些运行或测试证据。
- 你采取了什么措施，例如补充上下文、拆分任务、调整指令、查阅资料、人工修改代码或改变技术方案。
- 为什么采取这些措施。
- 修改后如何验证，最终是否达成目标。

重点展示“发现问题—分析原因—采取措施—验证结果”的完整过程。若仍有未解决问题，应如实说明其影响和后续改进办法，不得将未完成内容表述为已经完成。

## 四、截图与过程证据要求
1. 记录任务过程中的主要截图，必须包含全过程输入给AI的所有指令，包括首次需求、追加要求、修改要求、纠错指令和后续补充指令，不得只选取部分成功对话。
2. 长指令应使用连续截图完整呈现，确保文字清晰可辨；可另外附上完整对话导出记录，便于检索和核对。
3. 所有未达成目标的结果均须提供佐证截图，如错误界面、报错信息、测试失败、错误输出或与预期不一致的实际效果。
4. 每个问题的截图应配有必要文字说明，不能仅堆放截图。涉及修复的，应同时提供修复后的验证结果。
5. 截图按开发顺序编号，标明所属阶段、对应指令或问题，形成可追踪的过程记录。
6. 截图和日志中不得公开API密钥、账号密码及个人敏感信息。

## 五、最终产品要求
提交的最终产品应能够按照说明运行，并演示主要功能。报告中须包含：
1. 产品名称、用途和适用用户。
2. 实际完成的功能清单。
3. 运行环境、安装启动步骤和使用方法。
4. 主要界面及核心功能操作截图；无图形界面的软件提供运行结果截图。
5. 对照事先制定的验收标准，逐项说明是否达成及对应证据。
6. 已知问题、功能限制和后续改进方向。

## 六、代码提交要求
所有与本项目相关的代码须上传至Gitee，以备查阅。
1. 在Word报告中提供可点击的Gitee仓库链接，并标明最终提交版本的提交编号或标签。
2. 仓库须包含项目源代码、必要的配置示例、依赖说明及README。涉及数据库的，应提供必要的建表或初始化说明。
3. README须说明项目用途、运行环境、安装启动方法、主要功能和注意事项。
4. 不得仅上传截图、软件安装包、空目录或与项目无关的代码。
5. 不得上传真实API密钥、账号密码等敏感信息，可使用配置示例说明填写方法。
6. 保留能够反映主要开发阶段的提交记录，最终代码须与报告中的产品和截图对应。
7. 提交前检查教师能否正常打开仓库、查看代码；使用私有仓库的，须提前确保教师具有查阅权限。

无代码链接、代码链接无法打开或仓库代码为空，将影响最终成绩。

## 七、Word报告结构
请将以下内容整理为一份Word文档，命名为“学号_姓名_项目名称”。
1. 项目概述与需求分析。
2. 功能清单与验收标准。
3. TRAE、DeepSeek API及开发环境说明。
4. 方案设计与开发过程。
5. AI未达成目标的问题记录及解决过程。
6. 最终产品说明、功能截图与验收结果。
7. 个人总结。
8. Gitee代码仓库链接及最终版本信息。

其中，每个问题建议按照以下格式记录：

| 记录内容 | 具体要求 |
| ---- | ---- |
| 目标 | 当时希望完成的功能或修改 |
| AI指令 | 完整指令截图及编号 |
| 未达成表现 | 实际结果、与目标的差距及佐证截图 |
| 分析判断 | 对问题原因的分析、事实依据和推测 |
| 处理措施 | 补充指令、人工修改、资料查阅或方案调整等 |
| 验证结果 | 修改后的测试方法、实际结果及截图 |
| 最终状态 | 已解决、部分解决或未解决 |

个人总结应结合本项目说明：AI在哪些工作中提供了帮助，哪些环节需要人工判断，你采取的哪些措施有效，以及今后会如何改进开发与验证方法。不得仅写泛泛的工具体验。

## 八、评分标准

| 评分项目 | 分值 | 具体评分要求 |
| ---- | ---- | ---- |
| 项目需求与验收标准 | 10 | 使用场景、需求和功能范围清楚，项目具有实际功能（4分）；验收标准具体、可检查，需求变更有记录（4分）；技术与工具选择有合理说明（2分） |
| 开发流程与AI指令记录 | 15 | 开发阶段完整、过程连续（4分）；全部AI指令及关键输出记录完整，截图清晰、有序（6分）；有TRAE与DeepSeek API实际使用证据，并说明相互使用方式（3分）；过程、代码版本和结果相互对应（2分） |
| 问题处理与目标达成证据 | 15 | AI未达成目标的表现记录清楚，佐证截图完整（4分）；学生采取的措施具体，能说明分析与调整依据（5分）；修复后有运行或测试证据，能够判断问题是否解决（4分）；最终验收结果真实，遗留问题说明清楚（2分） |
| 个人分析与总结 | 10 | 结合具体案例分析AI未达成目标的原因，区分事实与推测（4分）；清楚说明个人判断、操作及其作用（3分）；总结工具能力边界、适用条件和后续改进方法（3分） |
| 最终产品与代码提交 | 5 | 最终产品说明、功能截图及运行方法齐全（2分）；Gitee链接可访问，代码完整且与产品对应，README及必要配置说明齐全（3分） |
| 报告规范 | 5 | Word结构清晰、表述准确，截图编号和文字对应，便于查阅（3分）；如实说明AI及其他资料的使用，妥善处理密钥与敏感信息（2分） |
| 合计 | 60 | |

### 评分补充说明
1. 不以项目规模、页面数量、代码行数或截图数量直接评定高低。重点看开发过程是否完整、问题处理是否体现个人判断、结果是否有证据支持。
2. 不按AI失败次数加分，也不得故意制造失败。应如实记录实际发生的问题及处理过程。
3. 未按要求使用TRAE与DeepSeek API的，工具使用证据对应的3分不得分；其余项目按实际提交材料评分。
4. 缺少部分AI指令的，根据缺失程度扣除指令记录对应分值；严重缺失、无法追踪关键过程的，该项对应6分不得分。
5. 无Gitee代码链接、链接无法打开或代码为空的，代码提交对应3分不得分；同时，依赖代码才能核实的功能、修复和运行结论，如无其他充分证据，不计相应证据分。
6. 最终产品未完全达成目标的，按实际完成情况和证据评分；完整、诚实的问题分析和处理记录仍可获得相应分数。
7. 允许AI辅助开发和整理报告，但学生须对代码、报告和结论负责。伪造相关截图、代码或测试结果，以及抄袭他人项目的，按学校相关规定处理。
