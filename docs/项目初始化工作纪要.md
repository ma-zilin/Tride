# 项目初始化工作纪要

记录日期：2026-11-06。本文单独保存初始化期间的工作与决定。

## 一、准备目标与依据

我为生成式 AI 课程项目准备了产品构想、Agent 协作方式、工具和版本管理。课程要求中的硬性标准已经转写并保存在项目的 [docs/作业要求.md](作业要求.md) 中，作为项目的唯一硬性依据。SRAD 软件工程材料、课程课件与参考书用于帮助选择方法，不额外增加评分要求。

产品构想从我的亲身经历出发。我结合自己管理任务、安排日程、使用课表和记录时间的实际体验，探查现有工具没有满足的真实需求，再思考哪些问题值得通过这个项目解决。产品构想由我自己撰写，访谈用于进一步明晰需求、核对约束和梳理取舍。个人任务、日程、课表、时间日志与 AI 协作等设想，都以这些经历和需求为出发点。产品构想描述目标和业务取舍，不等于正式需求规格，也不证明功能已经实现。

## 二、开发协作方式

开发架构以产品构想为起点。我分析项目规模、功能覆盖、预计投入、交付期限和课程验收要求等指标，参考软件需求分析与设计课程，以及生成式人工智能2课程的课件、案例和相关材料，比较不同开发过程与 Agent 分工方案，联合讨论后确定这套架构。具体取舍结合项目条件作出，并非直接照搬某份材料。

我选择增量迭代，结合风险验证推进开发。协调、需求、架构、开发、独立验证、证据整理、交付文档与决策顾问分别承担明确职责，采用独立会话；跨会话交接由我执行，协调 Agent 准备交接信息。

重要范围与架构取舍、验收标准和最终验收由我决定。独立验证可以写测试和报告，不修改业务代码。同一问题连续两轮开发修复与独立复测仍失败，暂停该问题并交回我判断。截图、失败现场、版本与报告之间保持可追溯关系。

## 三、工具与技能准备

工具与技能的选择来自我过去使用 AI Agent 开发的经验。我认为 grill-me 很适合通过追问暴露隐含假设、明晰需求和确定标准，因此希望在相关角色中复用。Superpowers 是热门的 SWE 项目，我将它作为开发、调试、代码评审和验证方法的参考来源，结合项目职责与边界选择其中的技能。过往经验和具体工作需要决定采用哪些能力，项目热度帮助我发现候选工具。

我确认 DeepSeek API 配置完成。本文不补写未提供的具体模型名称、调用参数或调用成功证据；课程要求的实际开发调用仍按原始记录取证。

项目采用项目级规则与技能。v2 安装包包含九个技能和两个公共规则：grill-me、grilling、test-driven-development、systematic-debugging、verification-before-completion、writing-plans、receiving-code-review、using-git-worktrees、tride-code-review。

技能尽量保留上游英文正文、示例、资源和许可证，只修改与我的角色边界、授权、取证及工具能力冲突的条款。代码审查采用内置版本的项目适配副本；普通源码审查不替代程序测试与实际构建。固定来源、差异、升级备份与回滚由安装包保存。

安装包与辅助脚本的历史离线记录为36项程序测试通过。这些结果只说明被测文件操作、升级回滚与夹具检查行为，不证明真实模型已遵守技能或工具权限已强制隔离。

## 四、Git 与双远端

课程要求将代码提交到 Gitee，而我平时更常使用 GitHub，因此我配置了双远端：Gitee 用于满足课程提交与教师查阅要求，GitHub 用于延续自己的开发习惯，并同步保存同一项目的代码与提交历史。

项目初始化已提交，分支为 main。本次检查时工作区干净，本地 Gitee、GitHub 的 main 远端跟踪记录均指向该提交；这不是本次联网查询两个服务的实时结果。

- Gitee：<https://gitee.com/meursin/tride>
- GitHub：<https://github.com/ma-zilin/Tride>

我确认 Git 配置完成。两个 remote 分别命名为 gitee 和 github，默认推送目标为 gitee，并配置了 `git pushall`：先推 Gitee，成功后再推 GitHub。双推不是跨服务的原子事务，一端成功不能证明另一端成功。

提交忽略规则排除了密钥、本地环境、技能备份、隔离演练和未整理的原始证据。

## 七、记录边界

在本次记录时，正式需求分析、产品技术选型、对应开发环境和业务实现没有作为本轮工作开展，项目中也未发现证据归档目录。角色在 TRAE 图形界面的逐项配置、真实 API 调用与强制权限隔离，不因文档或技能文件存在而自动视为已验证。
